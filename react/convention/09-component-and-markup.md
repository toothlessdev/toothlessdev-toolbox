# React Code Style – Markup, Component Split & Control Ownership

이 문서는 React 컴포넌트를 작성/리팩터링할 때  
"언제 분리할지", "마크업을 어떻게 구조화할지", "상태 제어권을 어디에 둘지"에 대한 규칙을 정의한다.

목표는 다음이다.

- 재사용 가능한 UI를 빠르게 만들고
- 읽기 쉬운 마크업 구조를 유지하며
- 상태 흐름을 예측 가능하게 설계하고
- 불필요한 리렌더링과 결합을 줄인다

---

# Glob Pattern

```
**/*.{tsx,jsx}
```

# 언제 이 규칙을 적용하는가

다음을 수행할 때 항상 적용한다.

- 컴포넌트 신규 작성
- 컴포넌트 리팩터링 (구조 변경, 분리, 합치기)
- state 위치 결정 (Parent vs Child)
- 복잡한 로직을 Custom Hook으로 이동할지 판단

---

# 1. 컴포넌트 분리 기준 (Three Pillars)

컴포넌트 분리는 "길이가 길다"는 이유만으로 하지 않는다.  
반드시 아래 세 기준 중 하나 이상에 근거해서 분리한다.

---

## 1.1 재사용성 (Reusability)

### MUST
- 프로젝트 내에서 **2회 이상 반복되는 UI 패턴**(Button, Input, Card 등)은 반드시 분리한다.
- 재사용 컴포넌트는 비즈니스 로직이 없는 **Presentational Component**로 작성한다.

### 판단 기준
- 여러 화면에서 같은 형태/행동이 반복된다
- props만 바꾸면 재사용 가능하다
- 특정 도메인 규칙이 박혀 있지 않다

---

## 1.2 의미 단위 분리 (Semantic Grouping)

### MUST
- 하나의 컴포넌트가 여러 맥락을 포함하거나 마크업이 비대해지면  
  **의미 있는 단위로 분리**한다.

### SHOULD
- 예: `UserProfile`이 커지면 `UserInfo`, `UserActivity`처럼 의미 기준으로 나눈다.

### 분리 신호
- "여기부터 다른 섹션인데..."라는 주석이 필요해짐
- JSX가 스크롤을 과도하게 유발함
- 동일 컴포넌트 안에서 서로 다른 목적의 UI가 섞임

---

## 1.3 제어권 기반 분리 (Control Management)

### MUST
- 상태가 여러 하위 컴포넌트에서 공유되어야 한다면  
  제어권은 **상위(Parent)** 에 둔다.

### SHOULD
- 컴포넌트 내부에서 완결되는 UI 상태(Modal open, Tab active 등)는  
  제어권을 **하위(Child)** 에 둔다.

---

# 2. 제어권 설계 규칙 (State Ownership)

상태 제어권 위치에 따라 컴포넌트 성격이 달라진다.  
따라서 설계 단계에서 명확히 선택한다.

---

## 2.1 상위 집중 제어 (Controlled)

### 대상
- 데이터 일관성이 중요한 폼 입력
- 여러 컴포넌트가 같은 값을 공유
- 상위에서 저장/검증/전송 흐름을 제어해야 함

### 구조
- 부모가 state를 소유
- 자식에게 `value`와 `onChange`를 전달

### 장점
- 데이터 흐름 추적이 명확
- 디버깅이 쉬움
- 검증/제출 파이프라인을 관리하기 좋음

---

## 2.2 하위 분산 제어 (Uncontrolled / Self-Contained)

### 대상
- 컴포넌트 내부에서만 의미가 끝나는 UI 상태
  - 드롭다운 열림/닫힘
  - 모달 open
  - 탭 선택
  - 아코디언 펼침

### 구조
- 자식이 `useState`를 내부에 선언
- 외부에는 이벤트 핸들러나 결과만 노출

### 장점
- 상위 리렌더링 최소화
- 컴포넌트가 캡슐화되어 재사용 쉬움
- 상위 컴포넌트가 단순해짐

---

# 3. 변경 빈도 기반 분리 (Volatility Isolation)

### MUST
- **자주 변하는 로직**과 **안정적인 UI**를 분리한다.

즉,
- 정책/규칙이 자주 바뀌는 부분은 Hook이나 별도 컴포넌트로 격리하고
- 안정적인 UI Shell에는 영향을 주지 않게 만든다.

---

# 4. 로직 및 부수 효과 분리 (Modern Hook Pattern)

컴포넌트는 렌더링이 본업이다.  
그래서 로직과 side-effect를 분리한다.

---

## 4.1 MUST

### Side Effect 분리
- Data fetching, subscription, timer 등은 반드시 Custom Hook으로 추출한다.

### 비즈니스 로직 분리
- 복잡한 계산
- 상태 조작 로직
- 분기/규칙 적용 로직  
→ 컴포넌트 내부가 아니라 Hook에서 관리한다.

#### 예시

```tsx
const { data, isLoading } = useUserFetch(userId); // Logic & Side Effect
if (isLoading) return <Spinner />;
return <UserDetail data={data} />; // Pure UI
```

---

## 4.2 MUST NOT

- 하나의 파일 안에
  - API 호출 로직
  - 대규모 JSX 마크업  
  을 동시에 작성하지 않는다.

---

# 5. 마크업 구조화 원칙 (Practical Rules)

이 문서의 핵심은 분리 기준이지만,  
마크업 자체도 다음 원칙을 따른다.

### MUST
- 의미 단위(Section / Header / Content / Actions) 기준으로 JSX 블록을 나눈다.
- 반복 구조는 `map` + 작은 컴포넌트로 분리한다.
- "div만 쌓는 구조"가 되면 의미 단위 분리로 해결한다.

### SHOULD
- UI Shell(레이아웃)과 Content(데이터 표현)를 분리한다.
- Action 영역(버튼 그룹)은 별도 컴포넌트로 분리한다.

---

# 6. 구현 체크리스트

컴포넌트를 작성하기 전에 아래 질문을 체크한다.

1. **재사용:** 이 UI가 다른 곳에서도 2회 이상 쓰일 가능성이 있는가?
2. **단일 책임:** 이 컴포넌트가 여러 의미를 한 파일에서 처리하고 있지 않은가?
3. **제어권:** 이 상태를 부모가 알아야 하는가, 아니면 여기서 끝내도 되는가?
4. **변경 빈도:** 자주 바뀌는 로직이 안정적인 UI를 흔들고 있지 않은가?
5. **성능:** 하위 상태 변경이 부모 전체를 불필요하게 리렌더링하고 있지 않은가?

---

# 7. Final Principle

좋은 컴포넌트는 작아서가 아니라  
**역할이 명확하고, 제어권이 정리되어 있으며, 변경에 강하다.**

분리는 "미학"이 아니라 "설계"다.
